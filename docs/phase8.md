# Phase 8 — Backend API

## Scope

This phase adds a local FastAPI layer over AVLOKAN's current local services. It does not create or modify the HTML/CSS/JavaScript frontend. Phase 9 can wire the existing controls to these endpoints.

## Frontend inspection

The entry page is `frontend/index.html`. It loads shared CSS (`variables.css`, `base.css`, `layout.css`, `components.css`, `main.css`) and view styles under `frontend/css/modules/` for login, dashboard, investigate, search, results, scene-map, analysis, review-audit, and color-studio. JavaScript is loaded from `frontend/js/data.js`, `helpers.js`, `router.js`, `topo.js`, `main.js`, and modules for dashboard, map-engine, investigate, search, results, scene-map, analysis, review-audit, and color-studio. Most views are constructed dynamically in the JavaScript modules.

The screens are login, dashboard, semantic search/results, AOI and scene selection, map explorer, multi-temporal analysis, change detection, verified evidence, analyst review, audit/history, and palette settings. The map and before/after/change views currently use a custom canvas renderer and deterministic synthetic drawing. They are not backed by map tiles or analyzer rasters. Search results, five dashboard AOIs, fourteen review candidates, scene timelines, status/feed entries, and displayed counts are hardcoded or generated in-browser. Palette settings use `localStorage`. No frontend HTTP requests exist today.

The UI's search-result shape includes scene/tile ID, coordinates, region, acquisition date, sensor, similarity, cloud, and thumbnail. Review cards currently display a `conf` percentage. The API does not invent such a confidence value: candidate records expose `candidate_score`, with `confidence: null`. Search coordinates and AOI map points use WGS84. The indexed catalog stores projected coordinates in some CRSs, so the retrieval bbox API accepts `bbox_crs` and transforms bounds per tile.

## Routes

All routes are under `/api`. Explicit Pydantic response models in `pipeline/api/schemas.py` describe dashboard counts, search result cards, scene timeline records, AOIs, analysis/candidate details, review state, and audit events. OpenAPI is available at `/openapi.json` and `/docs`.

| Route | UI / service need | Behavior |
|---|---|---|
| `GET /api/health` | System Status | Reports actual local index/catalog/checkpoint availability and counts. |
| `GET /api/dashboard` | Dashboard tiles/scenes/review/activity | Counts from the local tile catalog and API database; no demo totals are substituted. |
| `POST /api/search/text` | Text search and filters | Existing RemoteCLIP text encoder, FAISS index, tile catalog and metadata filters. |
| `POST /api/search/image` | Image query upload | Existing image encoder and the same local retrieval path; upload capped at 20 MiB and removed after use. |
| `GET /api/tiles/{tile_id}/preview` | Search result thumbnails | JPEG preview generated from a catalogued local raster. |
| `GET/POST /api/aois` | Map AOIs and registry | Persistent API-created WGS84 point/radius records. No synthetic AOIs are preloaded. |
| `POST /api/scenes/search` | Local AOI archive query/timeline | Spatial and date filters over `data/catalog/scenes.json`; it never makes a remote STAC request. |
| `POST /api/change-analyses` | Run Detection Pipeline | Validates allowed local inputs and calls the existing `ChangeAnalyzer`. |
| `GET /api/change-analyses/{id}` | Analysis evidence | Returns the stored structured analysis with candidates, stats, provenance-safe model identifiers, and artifact URLs. |
| `GET /api/change-analyses/{id}/artifacts/{kind}` | Swipe/evidence rasters | Serves probability, raw mask, candidate mask, metadata, and T1/T2 JPEG previews for a saved analysis. |
| `GET /api/changes` | Recent analysis records | Lists locally persisted analysis responses. |
| `GET /api/review-queue` | Review filters | Lists candidates generated by API-run analyses; supports pending, flagged, confirmed, rejected, or all. |
| `POST /api/review-queue/{id}/decision` | Confirm/reject/need review | Persists a decision and appends a hash-chained audit event. Final decisions cannot be replayed. |
| `GET /api/audit` | Audit filters/export data | Returns SHA-256 chain records and full-ledger integrity status. |

Text search accepts `query`, `sensors`, `top_k`, `date_from`, `date_to`, optional `bbox` in `[west,south,east,north]` order, `bbox_crs` (default `EPSG:4326`), `max_cloud`, and `min_similarity`. Search result rows keep fields useful to the existing result cards: `id`, `lat`, `lng`, `region`, `date`, `sensor`, `sim`, `cloud`, `thumbnail_url`, plus catalog identifiers and spatial metadata. Cloud filtering is applied only when a sensor/date cloud metadata join is unambiguous; missing cloud values remain null and are reported in `warnings`.

Scene records report `id`, `date`, `sensor`, cloud percentage, blocked state, quality metadata availability, bbox/footprint, and local availability. The API leaves the UI's `quality` value null because its local scene catalog does not supply a validated scene-quality score. Change-analysis outputs distinguish model probability, raw mask, and candidate mask; the existing `/mask.tif` becomes `candidate_mask` through the API. The API serves T1/T2 previews, but the UI still needs Phase 9 wiring to display them.

## Existing services and actual local inventory

The API calls `pipeline.retrieval.Retriever`, `RemoteCLIPAdapter`, `IncrementalIndex`, `TileCatalog`, local `scenes.json`, and `pipeline.change_detection.ChangeAnalyzer`. It does not duplicate model, embedding, or raster inference implementations. On this workspace the checked-in local artifacts currently report four catalogued/indexed tiles and ten scene-catalog records; the UI's 1.28M counter is demo text and is not returned as a backend count.

The API uses SQLite for records created through its routes: AOIs, API-run analyses, candidate review state, and audit events. It does not import the frontend's hardcoded demo review candidates. Audit events are SHA-256 chained and verification covers the full local ledger. The frontend's existing FNV-1a display logic is not reused as backend integrity verification.

## Run locally

Install the pinned API dependencies from `requirements.txt`, then start the service from the repository root:

```powershell
python -m pip install -r requirements.txt
uvicorn pipeline.api.app:app --host 127.0.0.1 --port 8000
```

Paths, local catalog/index locations, allowed analysis input roots, SQLite path, and CORS origins are in `configs/api.yaml`. Change-analysis checkpoint and operating settings remain in `configs/change_detection.yaml`. The server binds to loopback by default in the documented command. No API endpoint starts acquisition, downloads data, or trains a model.

## Limits before Phase 9

- The frontend is unchanged and still runs its demo data/interactions; no route is called by the browser yet.
- The local index has four vectors, not the dashboard's displayed 1.28M demo count.
- Scene search reads the local catalog only; it does not query STAC or retrieve products.
- Existing catalog records may lack cloud values. The API marks these unknown instead of treating them as clear.
- Analysis accepts server-local paths under configured input roots. It is not an arbitrary remote-file service.
- Candidate score is mean BIT probability for triage; candidate confidence remains null.
- The UI's demo authentication is not backend authentication. This local prototype is not an internet-facing deployment.
- Raster artifact URLs are ready for a later frontend integration, but the existing canvas components have not been changed.
